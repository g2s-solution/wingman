# wingman: design

Delegate work from one Claude Code session (the caller) to another Claude Code account (the target), so the caller can use the target like a subagent but on the target's own quota.

## Concepts

- **Profile**: one Claude account, identified by its config dir (`CLAUDE_CONFIG_DIR`). There is no fixed "A" or "B".
- **Caller**: the profile of the current session, detected from the MCP process's `CLAUDE_CONFIG_DIR` (unset = the default `~/.claude`).
- **Target**: any other profile in the registry. The caller is always excluded from its own targets.
- **Run**: one delegated job, executed by a detached `claude` process under the target profile.

Swapping roles needs no feature: start `claude` under another profile and that profile becomes the caller.

## Account registry

`~/.wingman/accounts.json`. It never holds credentials; login stays in each profile's own config dir. It lists the profiles; the caller names one by `id` or omits it and the server picks one at random among eligible targets (see Account selection). Selection policy, tags and scope arrive in v0.5 (see ROADMAP).

The CLI `wingman accounts list|add|disable|enable|remove` is the normal way to change it (`another-login.sh` calls `accounts add --upsert`); every write goes through the atomic `saveAccounts` (directory 0700, file 0600) and never touches credentials or profile directories. Status values are `active` (also when the field is absent) and `disabled`. The MCP tool `wingman_accounts` is read-only (id, label, status, `is_caller`, provider; no command, no paths) and no tool mutates the registry: an entry's `command` is executed by the runner, so a prompt-injected session must not be able to add one. Mutations stay in the CLI, run by the Human in a terminal.

| field | meaning |
|---|---|
| `id`, `label` | short name used by tools and skills |
| `config_dir` | profile directory |
| `provider` | agent backend, default `claude` |
| `command` | executable that starts the agent for this profile, default `claude`; for a profile made by `another-login.sh` it is the launcher (for example `~/.local/bin/claude-second`), which sets `CLAUDE_CONFIG_DIR` and loads that profile's credential |
| `scope` | data boundary (for example `company`); a run only goes to an account whose scope matches the work (v0.5) |
| `tags`, `priority` | selection hints (v0.5) |
| `status` | `active` (or absent), `disabled`, `rate_limited` (written back automatically when a run ends `rate_limited`, or by `wingman accounts mark-limited`) |
| `limited_until` | ISO time (UTC) when `rate_limited` ends; optional, so entries written before v0.4 stay valid |

Quota: every run records the `rate_limit_event` data the CLI emits (`status`, `resetsAt`, `rateLimitType`, `utilization`). That is per-run feedback, not a reliable pre-run gauge.

Limit state (v0.4):

- Write-back: when a run ends `rate_limited`, the supervisor converts `resetsAt` (unix seconds, from the rejected event) to `limited_until` and sets `status: rate_limited` on the run's account, before the run's own status flips. A missing or already-past `resetsAt`, and a `disabled` account, are left alone. The registry is read-modify-written without a lock; a concurrent edit by the Human can be lost, as with every other registry mutation.
- Expiry on read: there is no background job. An account is limited while `status = rate_limited` and `limited_until` is later than now; at that instant and after it reads as `active` (the stale fields stay in the file until the next mutation or `clear-limited`; `enable` and `disable` drop them). A `rate_limited` entry without `limited_until` stays limited until `clear-limited`; an unparsable `limited_until` counts as expired, so a bad value never locks an account out.
- The Human changes it with `wingman accounts mark-limited ID --until <ISO time with Z or an offset, a bare date (UTC), or epoch seconds>` (must be in the future; refused for a disabled account) and `clear-limited ID`. No MCP tool mutates it.
- Run summary: `wingman accounts list` and `wingman_accounts` report per account `runs: {total, by_status}`, counted from the terminal runs' `meta.json` only (running runs and `events.jsonl` are never read).

## Account selection

`account` is optional in `wingman_start`. When omitted, the server picks one at random among the registry targets that are not the caller's profile and are active (not `disabled`, not currently limited). When given, it must be a target that is active: a limited account is refused with an error naming `limited_until`. When a start is refused for a limit, or a run ends `rate_limited`, the tool response lists the other active accounts (`other_active_accounts` and a `hint` on `wingman_status` and `wingman_result`; the refusal message for a start); nothing is rerouted.

v0.5 (skill `pick-account`) replaces the random pick with a smarter one:

1. Hard filter: `status = active` and matching `scope`.
2. Match `tags` to the task (heavy implementation, cheap lookup).
3. Order by `priority`, then by fewest recent rate limits.
4. On `rate_limited` mid-run the server reports it; the caller decides to wait or start a new run on another account. The server never reroutes by itself.

## Child process environment

The runner builds the child's environment from an allowlist, never from the caller's environment: `PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`/`LC_*`, `TERM`, `SHELL`, `TMPDIR`, the proxy variables (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` and their lower-case forms), `CLAUDE_CONFIG_DIR=<target>`, `WINGMAN_DEPTH`. Every `CLAUDE_CODE_*`, `CLAUDECODE` and `ANTHROPIC_*` variable is dropped, because a desktop session sets identity, auth-refresh and messaging variables that would make the child behave as the caller's account or as a desktop child. The child keeps the proxy variables (DLP). **Credentials**: a profile signed in with a token (`another-login.sh`, `authMethod: oauth_token`) authenticates only because its launcher exports `CLAUDE_CODE_OAUTH_TOKEN` from the profile's `api-key.env`; with the credential variables dropped and `CLAUDE_CONFIG_DIR` alone, the child reports "Not logged in" (observed in Gate 0). So the runner execs the account's `command` (the launcher) with the allowlisted env and never reads, stores or forwards a credential itself; the launcher adds it. A profile signed in with `claude auth login` (credentials file in its config dir) works with `command: claude`. Tests: the credential variable is absent from the caller env handed to the runner and appears in the child only through the launcher. The runner's git commands run with the proxy variables removed (`env -u HTTPS_PROXY -u https_proxy -u HTTP_PROXY -u http_proxy`), because the internal git host rejects the proxy. The worktree is cut from the caller's local HEAD, so the runner never fetches and has nothing to retry. Every git command and the setup command runs under a timeout in its own process group, so a timeout kills the whole tree: `git worktree add` 60 s, the setup command 600 s, both overridable. The whole start phase (worktree add, setup) is capped at 15 minutes: each step gets at most the time left, so the phase always ends before reconcile's 20-minute no-pid grace. A timeout is a failed start that removes the run directory, the worktree and the lock.

## Run lifecycle

- The MCP server is a stateless control plane. Each run is a detached process (own process group); state lives in `~/.wingman/runs/<id>/` (`meta.json`, `events.jsonl`, `result.md`) so a run outlives the caller session. The child's stdout and stderr go to a file descriptor opened by the runner, never through a pipe to the MCP server, so the child does not get EPIPE when the caller ends.
- Runs are one-shot, like an ordinary subagent: there is no continue or resume. To give more work, start a new run. The runner still pre-assigns a session id (`--session-id <uuid>`) and records it in `meta.json` for diagnostics only.
- **Worktree**: when `cwd` is a repo, the run gets a worktree by default, cut from the **caller's current HEAD** (never from origin/base, so work the caller just committed is present), including when the caller is on the base branch: the run never touches the caller's checkout or base branch. A run branch is created only when the run may commit (the `edit-files` or `edit` preset, or explicit `allowed_tools`; override with the `branch` start parameter): `<caller-branch>-wm-<runid>`, or `wingman/<runid>` when the caller is on a base branch. A `readonly` run gets a detached worktree and no branch. The caller reviews the run branch and merges or fast-forwards it into its own feature branch. Without a worktree (`worktree:false`) a start on a base branch or detached HEAD is refused, and a detached HEAD is refused with a worktree too. The worktree lives under `~/.wingman/worktrees/<runid>`. A per-repo lock, keyed by repo and the optional `lock_key` start parameter, stops two runs from working on the same item; `lock_key` needs a worktree run and is refused with `worktree:false` or outside a repo.
- **Worktree setup**: a fresh worktree has no dependencies or ignored local config. The setup command comes from the `setup` start parameter or a wingman preset and runs before the task. `.env` files are never copied; checks that need local config are reported as Human items.
- **Run directory**: `meta.json` stores the effective `run_cwd` (the worktree plus the caller's subdirectory offset, computed from real paths, so a symlinked `cwd` works and a path that resolves outside the repo is rejected) and the repo toplevel.
- **Cleanup**: a worktree is removed when its run is accepted or discarded. `wingman_cleanup` refuses `accept` while the worktree has uncommitted changes (`discard` drops them), and refuses while another non-terminal run still references the same worktree. Orphans (terminal runs older than a day, or runs whose supervisor is gone) are pruned at server start, skipping dirty worktrees and worktrees a live run references; only a top-level server (`WINGMAN_DEPTH` 0) prunes, because a child run loads the wingman MCP server too. `events.jsonl` is cut to its last 20 MiB when a run finishes, and that of terminal runs finished more than 14 days ago is deleted at server start; the run directory, `meta.json` and `result.md` stay. Cancel kills the process group and checks pid against the recorded start time to avoid pid reuse.
- **Reconcile**: every tool path (status, result, cancel, cleanup, list), `waitForRun` and `wingman-wait` first ends a dead run: `running` with a recorded pid that is dead or whose start time no longer matches, or `running` with no pid recorded more than 20 minutes after creation (the start phase, with worktree and setup, must fit in it; `WINGMAN_NO_PID_GRACE_MS` overrides), becomes `failed_no_report` and is persisted. When the supervisor is dead but members of its process group (the agent) still run, reconcile (and `wingman-wait`) sends the group SIGTERM, then SIGKILL after 3 s; this is safe because a pid is never reused while it is still a group id. Orphan pruning keeps a worktree while any process of the run's group is alive. Every meta write during the start phase goes through a status-preserving patch that refuses a run reconcile already ended, so a slow start cannot resurrect it. `wingman-wait` has no default maximum wait: reconcile ends a dead run, and a hung agent is killed by the run's 4-hour wall-clock limit.
- **Supervisor end**: the supervisor finalizes on the agent's `exit` event plus a 2 s pipe drain, not on `close` (a grandchild holding the pipes would hang the run), then kills what the agent left in its process group. A result received before a timeout kill stands over `timedOut`.
- `wingman-wait <run_id>` blocks until the run ends; run it with Bash `run_in_background` so the caller is woken on exit instead of polling. It is a thin Node launcher for `wingman wait` in the server bundle (`dist/index.js wait`), which shares the reconcile and process code with the server. `proc.ts` reads `/proc` on Linux and `ps` (fixed arguments, `LC_ALL=C`) elsewhere.

### Run status

A run ends in one of: `done`, `partial`, `blocked`, `needs_input`, `needs_caller`, `failed`, `failed_no_report`, `rate_limited`, `cancelled`. The runner appends an instruction that the final message ends with a machine-readable line `WINGMAN_STATUS: done|partial|blocked|needs_input`. A missing line maps to `needs_input`; a child that exits without any result message (for example killed by a DLP block) maps to `failed_no_report`, so `wingman-wait` never hangs. A result that names an explicit `claude plugin install|update|uninstall` command, or says in one sentence with `claude` that a plugin was updated, maps to `needs_caller`. A run that stops at its turn limit (`error_max_turns`) maps to `partial`. A run whose base-branch ref, caller-branch ref or local git config changed while it ran (see Guardrails) maps to `needs_caller` with a note in the result, unless it already failed.

## Tools (MCP server `wingman`)

v0.1: `wingman_start`, `wingman_status`, `wingman_result`, `wingman_cancel`, `wingman_list`, `wingman_cleanup` (accept or discard: removes the worktree and lock, keeps the run branch when there is one), and the read-only `wingman_accounts` (see Account registry). Start takes optional `account` (random eligible target when omitted; an explicit one must be registered, active and not the caller's own profile), `prompt`, `lock_key`, `setup`, `cwd`, `model`, `preset` or `allowed_tools`, `max_turns`, `worktree`. `allowed_tools` items must match a conservative pattern and may not start with `-`, so an item can never read as a CLI flag. A start from a base branch (main, master, the origin HEAD target) is allowed with a worktree, which is the default in a repo: the run gets its own `wingman/<runid>` branch. Only `worktree:false` on a base branch is refused; a detached HEAD is refused with or without a worktree.

## Guardrails (in the server, not left to each brief)

- Every run gets an appended system prompt (through `--append-system-prompt`, or `systemPrompt: {type: 'preset', preset: 'claude_code', append}` in the SDK): never print or send sensitive values, never commit to the base branch, do not ask questions (inside a wingman run, "ask the Human" in any rule or skill means: stop and finish with `WINGMAN_STATUS: needs_input`), always end with a final report and the status line.
- No interaction: `--permission-prompts none` where available, `AskUserQuestion` disallowed. Permission denials are recorded and their tool names returned to the caller so it can widen the preset deliberately.
- **Permissions are a preset, not a bare allowlist.** Three presets. `readonly` (default) allows `Read`, `Glob`, `Grep` and read-only git. `edit-files` allows `Read`, `Glob`, `Grep`, `Edit`, `Write` and the same `Bash` git subcommands as `edit` plus `date`, but no `node`, `npm`, `Agent` or `Skill`; it may commit, so it gets a run branch. `edit` allows `Agent`, `Skill`, `Edit`, `Write`, `Read`, `Glob`, `Grep` and `Bash` for git, node, npm and date. `git push` is denied outright in both (pushing stays with the caller), because prefix rules on a push to the base branch are bypassable (`git -C . push`, `env git push`, `sh -c`). The deny list also names `git update-ref`, `git config`, `git remote`, `git send-pack`, `npm publish`, the option-prefix forms `git -C`, `git -c`, `git --no-pager`, `git --git-dir`, `git --work-tree`, and the file-writing `--output` forms of `git diff`, `git log` and `git show`. **Presets and deny rules are advisory, not a sandbox, and `edit` runs arbitrary code under the target account** (the `wingman_start` description and the skill say so): prefix rules are bypassable (`env git push`, `sh -c`), and `Bash(node:*)` (and `Bash(npm:*)` in `edit`) runs arbitrary code, so "denied" means the agent is told no and the permission layer refuses the obvious form, not that the action is impossible. Never `bypassPermissions`. The permission mode (`acceptEdits` versus `auto`, the shared settings default) is decided in Gate 0.
- **Ref snapshot (after-the-fact check)**: before the agent starts, the server hashes `git for-each-ref` of the base branches and the caller branch (never the run branch) and `git config --local --list` into `meta.ref_snapshot`. When the run ends the supervisor recomputes them; a change maps a `done`, `partial`, `blocked` or `needs_input` run to `needs_caller` and appends a guardrail note to the result. It cannot tell the run from the caller committing meanwhile, so the note says to check with git. It detects; it does not prevent. The snapshot also holds `hooks_hash`: a hash of the sorted names, sizes and content hashes of the files in `$(git rev-parse --git-common-dir)/hooks` (`*.sample` skipped; `core.hooksPath` is already covered by the config hash). A hook added, edited or removed while the run was active ends it as `needs_caller` with a note, because a hook runs arbitrary code on the caller's next commit. Metas written before `hooks_hash` existed simply skip this check.
- **No plugin management in a run**: `Bash(claude:*)`, `Bash(claude plugin:*)` and `Bash(npm install -g:*)` are disallowed. A run must not change the plugin cache under the caller's live session.
- **No recursion** (three layers, so role swap between two profiles cannot loop):
  - Hard: `WINGMAN_DEPTH` (default limit 1) is set in every child run by the adapter's env allowlist and `assertCanStart` refuses a start when it is set, whichever accounts are registered; the wingman MCP tools are disallowed in child runs (`--disallowedTools "mcp__plugin_wingman_*"`) and `--strict-mcp-config` is on the child command line, so no MCP server loads in a child run even though the plugin is enabled in every profile through the shared `settings.json`.
  - Prompt: rule 4 of the appended system prompt tells the run it is delegated, must not use the wingman tools, the new-agent skill or another Claude Code process, and must do the work itself or finish `blocked`. The `new-agent` skill also tells the caller not to ask a run to delegate.
  - Hook: the plugin's SessionStart hook prints nothing when `WINGMAN_DEPTH` is set, so the "prefer new-agent" instruction is never injected inside a run.
  - Why role swap cannot loop: A delegating to B starts B with depth 1; B has no wingman tools (hard), is told not to delegate (prompt) and is not nudged toward it (hook), and a start from B would be refused anyway. Registering both profiles in a shared registry therefore adds no path back from B to A. The caller itself is also excluded from target selection.
- **Output to the caller is masked and paged**: status returns a short status; `wingman_result` returns the final message after a secret-pattern mask, in pages (`offset`, `limit`; default 4000, max 8000 characters) with `result_total_chars` and `result_next_offset` (absent on the last page), so a long report is never silently cut. The whole report is masked first and sliced after, so a secret split by a page boundary cannot escape the mask (bearer, JWT, keys, passwords, URL credentials). Raw `events.jsonl` and tool output are never returned.
- **Known limits**: the prompt travels to the child over stdin (never argv, env or disk), so it is not visible in the process list; the appended system prompt is still an argument (`ps`, `/proc/<pid>/cmdline`), which is fine because it is static guard text and not secret. `proc.ts` has two backends: `/proc` on Linux, and `ps` on macOS and other POSIX systems (start time for the pid-reuse check, group members for the orphan-group kill); the `ps` backend is unit-tested with canned output and exercised by the macOS CI job, but has had little real-world use. `setup` is an arbitrary shell command run as the caller's user, outside the presets.
- **Files on disk**: `~/.wingman` is mode 0700, files 0600, with automatic retention for `events.jsonl` and orphan worktrees. Run directories are removed only by `wingman gc` (manual; default 30 days after `finished_at`, terminal runs only, never a branch, plus stale lock files). The caller skill forbids reading `events.jsonl` and run logs; to review a run it uses `git diff --stat` and a sensitive-word `grep -c` before reading any hunk.

## Packaging

A Claude Code plugin named `wingman`: MCP server declared in the plugin's `.mcp.json`, skills (`new-agent` in v0.1; `pick-account` and `add-account` later), and the helper CLI. Plugin install copies the git tree and runs no build, so the server is committed as a single bundled file (`server/dist/index.js`, esbuild, MCP SDK included) and `.mcp.json` points at `${CLAUDE_PLUGIN_ROOT}/server/dist/index.js`. "Build at install" is not an option. The plugin is installed in the caller's profile only (`/plugin install`, user scope); `another-login.sh` shares `plugins/` with the default profile, so the plugin is installed in every linked profile at once, and a target never needs wingman because runs start with `--strict-mcp-config`. The symlinked `settings.json` carries `enabledPlugins` to every profile. A profile that does not share `plugins/` needs its own install to delegate.

## Doctor

`wingman doctor [--online] [--json]` (`src/doctor.ts`) is a read-only health check. Each check yields `{id, level: ok|warn|fail, message}`; exit 0 without a `fail`, 1 with one, 2 on bad usage. Offline it covers the state directory and registry (modes, parse, duplicates), each account (`config_dir`, launcher, own-profile as an informational ok, status), shared items versus the default profile (broken link is a fail, a forked item only a warn since sharing is optional) and the installed plugin version per profile. `--online` runs `<command> auth status --json` through `execFile` (fixed arguments, 20 s timeout) and reports only signed in, `authMethod` and whether the account differs from the caller, by comparing a sha256 of `email` and `orgId`; the identity and the raw output are never printed. All environment access (env, home, exec) is injected so tests are deterministic.

## Backends

v0.1 supports Claude Code only, but the runner is written against a small adapter interface: build the command, set the account selector env, inject the guardrail prompt, parse events into a common shape (`started`, `message`, `tool`, `rate_limited`, `finished`), and report the session id. Registry entries have a `provider` field (default `claude`). Other providers (OpenAI Codex, OpenCode, and similar CLIs) are added as further adapters in v0.7; the guardrails and the capped-report rule stay in the server so they apply to every provider.

## Engine

Candidates that were compared by testing under a real second profile (the initial verification, called Gate 0 in the history notes): the Agent SDK (`query()`; leave `settingSources` unset so user, project and local settings load; `env` replaces the whole environment; `systemPrompt` preset with `append`); `claude -p --output-format stream-json --verbose`; and Claude Code's built-in background sessions (`--bg`, `claude agents --json`, `claude logs`, `claude stop`), which could replace much of the detach, list and cancel code. `--max-turns` works but is hidden from `--help`. `--bare` is not usable (it never reads OAuth). Default if equal: `claude -p` stream-json.

### Engine decision and verification

- **Engine: `claude -p --output-format stream-json --verbose`** (default, nothing argued for another). Permission mode `acceptEdits`; the `auto` comparison is deferred.
- Verified under the second profile through its launcher, started with `env -i PATH HOME`: `-p` runs, a harmless installed skill expands under `-p`, and this command line is accepted: `-p <prompt> --session-id <uuid> --append-system-prompt <text> --disallowedTools <names...> --permission-mode acceptEdits --permission-prompts none --max-turns <n> --output-format stream-json --verbose`. `--strict-mcp-config` and `--plugin-dir` exist; `--max-turns` is hidden from `--help` but works. The adapter later added `--strict-mcp-config` to the child argv (right after `--verbose`); this is **verified against the real CLI**: real runs on the second profile completed with it, and no MCP server loaded in the child.
- Event contract (keys): `system/init`, `system/hook_started`, `system/hook_response`, `assistant` (`message`, `session_id`, `uuid`), `rate_limit_event` (`rate_limit_info`: `status`, `resetsAt`, `rateLimitType`, `isUsingOverage`, `overageStatus`, `unifiedWindows`; no `utilization` key seen on an idle account), `result/success` (`result`, `is_error`, `num_turns`, `permission_denials`, `stop_reason`, `session_id`, `duration_ms`). The final message is `result.result`.
- **Open (not verified)**: spawn from inside a real MCP server (covered by verification step 8.1), settings-symlink survival (the `installed_plugins.json` comparison only matters if `plugins/` is shared), `--bg`, detached survival after the desktop session ends, `Agent` allow under `-p`.

## Decisions

- **`projects/` is not shared between profiles.** Each profile keeps its own session history. Benefit: no concurrent writes to the same session files and no mixing of transcripts.
- Shared via symlink from the default profile by `another-login.sh`: `CLAUDE.md`, `settings.json`, `skills`, `agents`, `commands`, `rules`, `plugins` (only the ones that exist; plugins are shared on purpose so every profile has the same plugins, skills and settings, which role swap needs). Per profile, not shared: credentials, `.claude.json`, history, `projects/`. An existing real `plugins` directory is never moved by the script or by doctor; both print the manual commands (`mv <dir>/plugins <dir>/plugins.bak && ln -s <default>/plugins <dir>/plugins`).
- User-scope MCP servers (for example an MCP server for an internal tool) live in each profile's `.claude.json` and are not shared; add them to a target only if its runs need them.
- Profile identity is checked with `claude auth status --json` (compare account or organization fields and print only same or different), not with file mtimes: the default profile's credentials file changes on every token refresh.
- `CLAUDE_CONFIG_DIR` is not in Anthropic's documented settings, so treat it as working but unsupported.
- Interaction rules in the shared `CLAUDE.md` (ask the Human, open a new session) are redefined for wingman runs by the appended prompt (see Guardrails).

## Known risks

- Symlinks can break after a Claude Code update recreates a directory, or if Claude Code rewrites `settings.json` by temp file and rename, which would replace the symlink with a real file and fork settings. A check that a setting changed in the second profile leaves the symlink intact has not been automated; a health check is planned (see ROADMAP).
- `plugins/` is shared between profiles, so they all write `installed_plugins.json`, `known_marketplaces.json`, `synced/` and `data/` on startup and plugin sync, and installing or updating a plugin in one profile affects all. A run in flight can fail if a plugin is updated meanwhile. This has not been verified at runtime with two live profiles.
- Updating the plugin while a run is in flight can fail the run.
- Hooks that hard-code `~/.claude` run in every profile; keep hooks path-agnostic.
- Not verified at runtime: whether a plugin skill invoked by name expands under `-p`; whether `rate_limit_event` appears in stream-json; whether plugin stdio MCP servers receive `WINGMAN_DEPTH`; whether `--bg` works under a custom `CLAUDE_CONFIG_DIR`; whether detached children survive the desktop app ending a session; whether the `Agent` tool needs an explicit allow in `-p`; how a worktree path with no plugin install entry resolves project-scope plugins; whether the second profile receives its own `remote-settings.json` proxy (check presence with `ls` only).
